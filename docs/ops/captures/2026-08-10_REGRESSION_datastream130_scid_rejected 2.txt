2026-08-10 — REGRESSION CAPTURE: the box refuses iOS's RCS iAP-channel SETUP (stream type 130)
===============================================================================================

Source box file: /tmp/airplayd_wl.log (tmpfs), pulled over the root UART console during a live
wireless session with an iPhone on iOS 27, Apple Music PLAYING. Excerpted by grep with original
line numbers preserved (the "N:" prefix is the line number in the source log).

WHY THIS CAPTURE EXISTS
-----------------------
docs/carplay/05_METADATA_AND_CONTROLS.md established (2026-07-25) that inbound wireless iAP2 — i.e. the ENTIRE metadata plane —
rides an RCS DataStream, SETUP stream type 130. A guard committed in 5ce9d1c (2026-07-31) rejected
any SETUP stream whose `streamConnectionID` was 0 or absent. Type 130 legitimately carries NO
`streamConnectionID` (docs/carplay/05_METADATA_AND_CONTROLS.md §1.3; it keys off `seed` instead), so the guard rejected every one.

Effect: no `streamID` transport token was ever returned, so the phone's outbound iAP2 path never
existed, so the tunnel never left `Init` and NOT ONE metadata record could arrive — while A/V
looked perfect, which is why it hid for ten days. The owner reported "no metadata for several
sessions"; this capture is what closed the diagnosis.

Fix: narrow the guard to an ALLOWLIST of the types whose key derivation actually consumes scid —
`if scid == 0 && matches!(ty, 100..=102 | 110 | 111)` (crates/vendor/receiver/src/session.rs).
Deliberately NOT the deny-list form `ty != 130`: a deny-list re-applies an A/V-only rule to every
stream type Apple adds next, which is precisely how this outage happened. See docs/carplay/05_METADATA_AND_CONTROLS.md §1.3.

IMPORTANT SCOPE NOTE — this capture does NOT prove the current code path works
------------------------------------------------------------------------------
At the last 2026-07-25 commit (c1c5901) `session.rs` contained NO type-130 handling, NO scid
guard and NO key probe, and `datastream.rs` did not exist. The code that produced the SUCCESS
capture above was never committed in that form; it was folded into — and substantially rewritten
by — 5ce9d1c, the same commit that added the guard that made it unreachable.

So the 2026-07-25 capture proves the PROTOCOL SHAPE (the phone omits streamConnectionID, expects
`streamID` back, wants a dedicated socket, salts from `seed`). It does NOT prove the present
implementation of the 130 arm, which has ZERO hardware hours. Removing the guard makes that arm
reachable for the first time; treat the next session as a first-run of it, not a restoration.
