2026-08-10 — DEVICE EVIDENCE: metadata tier `all` is REJECTED on the AirPlayTunnel Identify,
and the phone names exactly which message ids it refuses.
================================================================================================

Source: /tmp/airplayd_wl.log on the box, live wireless session, iPhone on iOS 27.
Pushed config at the time: `metadata: {tier: all}` (the app's Settings value, persisted).

WHY THIS CAPTURE EXISTS
-----------------------
This is the FIRST time this project has seen a decoded 0x1D03 naming individual message ids on the
tunnel arm, and it only became visible today. Before the type-130 DataStream fix
(`32227ff`, see 2026-08-10_REGRESSION_datastream130_scid_rejected.txt) the inbound path did not
exist: we sent the tunnel Identify and never received the reject, so the link simply sat at `Init`
looking like a transport failure. With inbound restored, the phone's answer arrives — and it is
specific.

It also confirms, on hardware, the docs/carplay/05_METADATA_AND_CONTROLS.md §6.5 rule: ASK THE PHONE, DO NOT BISECT. One line of
decoded reject replaces what would otherwise be a tier-by-tier hardware bisection.

THE EXCHANGE
------------

[iap-tunnel] RX 0x1D00 -> IdentSent
[iap-tunnel] RX 0x1D03 IdentificationRejected raw payload (21 B):
             [40, 40, 00, 14, 1d, 03, 00, 08, 00, 06, 56, 0f, 56, 11, 00, 06, 00, 07, 56, 10, ff]
[iap-tunnel] RX 0x1D03 decoded: param 6 unsupported: 0x560F StartVoiceOverCursorUpdates,
             0x5611 StopVoiceOverCursorUpdates; param 7 unsupported: 0x5610 VoiceOverCursorUpdate
[iap-tunnel] TX 0x1D01 retry, stripped [6, 7] (372 B, AirPlay tunnel)      <-- BYTE-IDENTICAL
[iap-tunnel] RX 0x1D03 -> IdentRetried
[iap-tunnel] RX 0x1D03 IdentificationRejected raw payload (21 B): [ ...same... ]
[iap-tunnel] tunnel session aborted (second IdentificationRejected) — clearing

Session counters over a 10-minute soak: 0x1D03 = 5, 0x1D02 = 0, Identified = 0, NowPlaying = 0.
A/V unaffected throughout (main lane :9001 44/s recv+fwd, alt :9005 33/s, decryptFail = 0,
DataStream(130) established = 2, type-130 refusals = 0, oracle divergence = 0).

WHAT IT PROVES
--------------
1. **`all` is refuted on the AirPlayTunnel arm** — but ONLY for `voice_over_cursor`. The phone
   rejects three ids, not the tier as a class. CLAUDE.md records `extended` as accepted once on this
   arm (2026-07-25); this capture does NOT contradict that, and `extended` remains untested against
   this failure.
2. **The retry is byte-identical, so the reject is unrecoverable within the session** — exactly as
   CLAUDE.md states. Params 6/7 are in `REQUIRED_IDENT_PARAMS` and cannot be stripped, so
   `stripped [6, 7]` produced the same 372 B and drew the same reject. This is the documented
   behaviour working as designed, observed end to end for the first time.
3. **The ids map to a single feature-table entry**: `features.rs` `voice_over_cursor`
   (`Trigger::Subscription { start: 0x560F, stop: 0x5611 }`, `updates: &[0x5610]`). So the tier is
   salvageable with the EXISTING skip lever rather than a code change:

       metadata:
         tier: all
         skip: [voice_over_cursor]

   (App: Settings > Configuration > Advanced Capabilities > "Metadata skip", comma-separated.)
   TRIED THE SAME NIGHT AND REFUTED — see the FOLLOW-UP section below before acting on this.
4. **Params 20 and 21 are NOT named in the reject.** That is positive hardware evidence that the C-1
   / C-2 vehicle-identity work deployed the same day is genuinely parse-only: had the pushed identity
   reached the wire, the phone would have objected to those params. Stronger evidence than the test
   suite can give.

FOLLOW-UP, SAME NIGHT — THE SKIP WAS TRIED AND IT DID NOT RESCUE THE TIER
------------------------------------------------------------------------
Owner set `metadata: {tier: all, skip: [voice_over_cursor]}` and rebooted for a fresh first-arm.

Armed correctly:  metadata policy ARMED from pushed config: tier=all skip=["voice_over_cursor"]
The skip WORKED mechanically: the Identify went 372 B -> **366 B**, i.e. exactly 6 bytes / three ids
at 2 bytes each. `voice_over_cursor` was genuinely removed, as
`features::skipping_voice_over_cursor_removes_exactly_the_refused_ids` predicts.

**iOS rejected it anyway, and this time named nothing:**

    [iap-tunnel] RX 0x1D03 decoded: param 6 (no detail)

Counters for the session: 0x1D02 = 0, 0x1D03 = 5, NowPlaying = 0, DataStream(130) = 2 (transport fine).

WHAT THIS ESTABLISHES — and it is more useful than the original capture
----------------------------------------------------------------------
1. **`all` is refused for MORE than `voice_over_cursor`.** The named-id reject was a real objection,
   but satisfying it only exposed the next one.
2. **The phone enumerates ids only while it has a SPECIFIC complaint.** Once the specific one is
   satisfied it falls back to the generic `param 6 (no detail)` marker — the same signal docs/wireless/00_WIRELESS_CARPLAY.md recorded and could never resolve. So **iterative skipping is a dead end from here**:
   there is nothing left to read, and the only remaining route is bisection, which docs/carplay/05_METADATA_AND_CONTROLS.md §6.5
   exists to prevent us spending sessions on.
3. A prediction was made and REFUTED. The lead's reasoning was "the ids map to one feature entry, so
   the existing lever should suffice", with the caveat that only the phone could confirm. The
   mechanism was right (366 B proves it); the conclusion was wrong. Recorded as a refutation rather
   than quietly dropped, per the project's own standard.

**CONSEQUENCE FOR THE TIER LADDER:** `all` should be treated as REFUTED on the AirPlayTunnel arm
until someone has a reason beyond "try skipping things". `extended` remains the largest declaration
this hardware has been OBSERVED to accept (docs/carplay/05_METADATA_AND_CONTROLS.md §6.6, 2026-07-25: 340 B, RX 0x1D02 -> Identified,
8 subscribes, every declared feed arriving) and is the right next value. `proven` is the guaranteed
floor.

HOW TO READ THIS DOCUMENT AS A WHOLE
-----------------------------------
The named-id reject at the top and the generic reject in the follow-up are ONE result, and the
follow-up supersedes the top section's advice. "Drop the named feature and ask the phone again" was
the right FIRST move — it is what produced the 366 B evidence — but it is not a strategy, because the
phone stopped naming ids as soon as its specific objection was met.

Net position on the AirPlayTunnel arm, as of 2026-08-10:
  * `all`      — REFUTED. Rejected with named ids; rejected again, generically, with those ids gone.
  * `extended` — the largest declaration OBSERVED accepted here (docs/carplay/05_METADATA_AND_CONTROLS.md §6.6, 2026-07-25).
  * `proven`   — the guaranteed floor.

RESOLUTION, SAME NIGHT — `extended` WAS SET AND ACCEPTED
-------------------------------------------------------
tier=extended, skip cleared, adapter rebooted for a fresh first-arm:

    metadata policy ARMED from pushed config: tier=extended skip=[] (first arm wins)
    TX 0x1D01 IdentificationInformation (342 B)
    0x1D02 = 1 (ACCEPTED)   0x1D03 = 0   NowPlaying = 388 in ~90 s   artwork = 2
    0x4158 CommunicationsUpdate = 2   <-- the telephony feed `proven` cannot declare
    decryptFail = 0

The ladder on this arm is therefore closed empirically:
    proven    ACCEPTED (device-proven, the recovery floor)
    extended  ACCEPTED (device-proven twice: 2026-07-25 @340 B, 2026-08-10 @342 B)
    all       REFUTED  (named-id reject, then a generic reject with those ids removed)

Operational note for whoever repeats this: DO NOT hand-edit `/tmp/carplay_cfg.yaml` to change the
tier. `ocbmd` rewrites that file from the app's push at every CT_SUBSCRIBE, BEFORE it flips
`/tmp/host_present`, and the supervisor only starts the phone-facing daemons on that presence edge —
so a hand-edited file is always overwritten before any daemon reads it, and you would be measuring
the app's persisted value while believing you were measuring yours. Going app-less does not help
either: no SUBSCRIBE means no session. Change the SOURCE:

    defaults write zeno.carlink.mac vc.metadataTier -string "extended"
    defaults write zeno.carlink.mac vc.metadataSkip -string ""

then restart the app (it pushes at SUBSCRIBE) and reboot the adapter (the tier is first-arm-wins per
process, so a live link never picks up a change).

This still does NOT say the tunnel Identify must stay at `proven`, and it says nothing about the
WIRED arm, which has its own history. It says `all` costs a session and tells you nothing you can act
on, so stop paying for it.
